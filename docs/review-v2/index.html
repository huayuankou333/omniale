01 / TASK DEFINITION

任务定义

委托场景：审片结束后，制作团队需要把制片人确认的修改与技术故障落实到工单系统。最终交付是数据库中的记录、负责人、优先级与状态；文字总结不能替代实际更新。

依据项目定义，D1 以程序、配置或业务状态改变为主要交付。本题采用可持久化的本地业务 API；Case 2 与 Case 3 则以应用修复为交付。素材为程序图形与合成语音构建的受控工作流。

给 Agent 的材料

review.mp4 · 原始合成审片会议。黄色 ON AIR 标识实际播放对象；蓝色键盘焦点可能位于另一个播放器。

证据与可操作环境

1 份 SOP、1 段会议录屏、13 个源视频与对应音轨、包含 8 条历史工单的初始数据库。

工具可读取状态、抽帧、生成连续联系表、独立转写和测量左右声道；变更通过原子事务保存。

本次实际输入路线：通用模型＋每 10 秒抽帧＋独立 Whisper ASR＋可调用 PCM 信号测量。任务素材包含音视频，但模型没有直接接收原始音视频流；这是工具辅助感知试评。

需要处理的关键约束

  • NORA 批准的最终决定有效；JAY 的提议不能自动变成任务。
  • 画面意见要在重排、重定时后的 v3 交付版重新定位。
  • 音频故障属于实际试听版本，不能一律迁移到 v3。
  • 旧诊断需撤销并另建真实故障；无关历史不能误改。

05 / REPRODUCIBILITY
案例文件与可比性
本次沿用同一任务、审片视频、源素材、真值、评分器与媒体工具。运行预算为 40 轮，推理设置为 medium，单次最大输出 9,000 tokens。网络恢复仅重发请求或从已完成轮次继续，不重新执行已完成的系统写入。
运行器为网络重试与断点恢复增加了记录，因此 harness 哈希不一定相同；模型输入任务与工具定义不随评分改变。GLM 的诊断输入条件不同。来源于现有开发集的单次试评不能估计稳定排名、pass@3 或泛化能力。
