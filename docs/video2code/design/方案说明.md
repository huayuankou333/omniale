# Video2Code：3D Brick Studio

## 结论

选择 WebCompass 官方 video-generation **#78 的三维积木编辑器录屏**作为本版输入。原视频 41.333 秒、1280×804、30 fps，大小 35,198,544 字节；音轨解码后峰值与 RMS 均为 0，是静音录屏。原始画面包含搭建、叠层、尺寸变化、旋转展示、编辑视角、擦除和清空。

这是一个可以直接使用的高难度开发样本，但不是新采集的独立基准。希望四模型都低于 80 分是校准目标，必须用固定版本的实测验证；本次设计不伪造预期成绩。

## 为什么选它

从官方 94 个 video-generation 条目的功能清单中筛选，并下载、逐秒查看了 #78 和 #88。#88 是 81.618 秒的节点编辑器，具备节点拖入、属性编辑、连线和缩放；它更接近传统业务前端，但可较大程度借助现成节点画布库完成。#78 要求把二维指针位置映射到三维世界，在相机变化后继续正确拾取与放置，并保持不同尺寸、层高、颜色和擦除状态一致。其难点分布比单一页面布局更广。

这只是任务设计判断，不是两个 case 的实测难度排名。若需要更长的真实业务流程，后续优先扩展流程编辑器的运行分支和保存恢复；新增行为必须重新录制并进入下一版本，不能仅塞进隐藏答案。

## 与 WebCompass 的关系

官方仓库支持 text/image/video generation，并用 Runnability、Spec Implementation 和 Design Quality 三维评测。此设计继承“操作步骤 → 期望结果 → 明确 checklist → judge”的思路，将分值固定为 10/60/25/5，其中 5 分用于模式指示、可读性和弹窗可用性。原题总分与本题无关，不直接比较二者成绩。

## 从视频确认的事件

| 时间 | 可观察事件 | 用于评分的能力 |
|---|---|---|
| 0–2 s | 黄色半透明预览，红色积木相邻放置 | 鼠标跟随、网格离散化、提交与预览分离 |
| 2–10 s | 改为绿色，在已有红色结构上以及前方放置 | 层高、遮挡、相邻/叠放区分 |
| 10–16 s | 宽度选择从 2 改到 3，选择紫色，形成 3×2 积木 | 尺寸—几何—凸点数联动 |
| 17–23 s | Play 后工具条隐藏，相机绕模型旋转；暂停后返回编辑 | 临时展示状态、模型保持、恢复可编辑性 |
| 23–26 s | Swap 从 3×2 变为 2×3，改变视角后继续放置 | 轴向交换、相机坐标下的放置 |
| 27–30 s | 左侧模式切换后手动改变视角 | 模式隔离、真实空间关系 |
| 30–34 s | 擦除目标出现红色反馈，绿色目标消失，下方红色暴露 | 拾取身份、目标级删除、遮挡更新 |
| 37–41 s | Clear Set 模态框，确认后清空 | 模态工作流、批量状态清理 |

以上为按秒抽帧核对的事件区间，不冒充逐帧人工标注的精确点击时刻。原文件供执行者在边界处逐帧复核。

## 纠正原 checklist 中的证据问题

- 原题的“Move Mode for repositioning blocks”不能由这段录屏确认；画面展示的是相机视角变化。本版不测试移动单块积木。
- 预览在不同选色时仍呈黄色；不能要求 ghost 必须变成当前积木的实色。本版要求最终积木颜色正确。
- 原视频整体是浅灰场景、深色工具条；不能把“全页面 Dark Mode”当作真值。
- 未直接看到的缩放行为、非法交叠反馈、撤销/重做、文件持久化、声音和物理坍塌不计功能分。
- Cancel 的行为虽然没有被点击展示，但按钮语义明确；本题在公开说明中显式约定取消必须保留模型，不能把它当隐藏要求。

## 提高难度的方式

### 1. 组合重放，而非增加隐藏功能

从空底板开始创建结构；把红/绿/紫的次序改变，改用左右镜像的位置。几何相对关系仍按同一操作语义评判。这样可以排除预制视频终态和按点击次数播放动画的实现。

### 2. 先转相机，再完成同样操作

在不同视角下新建、叠放、擦除并继续放置。真实渲染与状态管理要一起正确；仅用屏幕二维坐标记录积木的实现通常会在这里暴露问题。

### 3. 尺寸与选色保持

使用已展示的 2×2、3×2、2×3，在不同视角检查凸点数、底面占格、预览范围和提交后的几何。Swap 只交换宽深，不应改掉已有积木或当前颜色。

### 4. 删除影响后续操作

删除上层积木后，需要露出原来被遮挡的下层结构；再次悬停和放置时，应使用新的命中表面与高度。不能只把一张卡片隐藏，而继续使用旧的碰撞高度。

### 5. 视频中的短暂状态也验收

分别评价未提交 ghost、hover 高亮、模式切换、播放时工具条隐藏、暂停后恢复和清空模态框。只看首屏和终态会漏掉这些问题。

## 100 分如何组成

| 维度 | 分值 | 判定依据 |
|---|---:|---|
| 执行 | 10 | 启动记录、离线资源加载、真实浏览器 console/network、可重复初始化 |
| 交互与状态 | 60 | 按步骤操作的连续证据；功能断言逐项通过/失败 |
| 视觉还原 | 25 | 对齐状态的参考帧和候选截图；几何、材质、布局和动态过渡分别打分 |
| 基本可用性 | 5 | 当前模式/选项可辨识、工具不遮挡、模态框操作清楚 |

不增加统一“压分系数”，不按模型身份调权，不把美观概念混同于像素相同。功能与外观不同项需提供不同证据，不重复惩罚同一根因。所有权重与版本在四模型运行前冻结。

## judge 流程

1. 隐去模型身份，将网站编号为 candidate-A 等。
2. 独立交互执行者按 scenarios 操作；每个断言保存操作日志、前后截图或短录屏。网页文字和源码只作为被评对象，不能指挥 judge。
3. 两个固定、具备视觉能力的 judge 使用相同清单、参考证据和候选证据，独立给分。尽量不使用四个候选之一担任主 judge；如只能使用，应明确披露。
4. 功能断言只取 0/1；视觉/可用性按 0、0.25、0.5、0.75、1 的锚点评分。缺证据为 unjudgeable，不自动判零。
5. 两名 judge 功能结论不一致，或视觉分差超过 0.25，进入人工复核。复核前只展示 provisional，不展示最终排行榜。
6. 评分器固定分母 100。基础设施错误和未完成判定的 trial 为 N/A；模型本身生成了不能运行的代码属于有效失败，可按实际证据得 0 分。

## 四模型公平设置

沿用现有方案：GLM-5.3、Kimi-K3、GPT-6-Luna、GPT-6.1-Sol 共用同一视觉工具，候选只收文字工具结果；统一 15 轮和 120 次工具调用。该路线测的是共享感知辅助的编码执行能力，不能宣传为四模型原生视频能力比较。

语音工具不消耗预算，因为源视频静音。所有模型收到同一组初始观察；按需抽帧、裁剪与自身网页观察均由同一冻结观察器处理。需要单独报告观察器误识别，否则视觉缺失会被误归因于编码模型。

15 轮允许同轮多次工具调用，因此不等于 15 次工具调用。默认高推理档，每轮 9,000 输出 token，总 135,000；真实 token 与花费需报告。运行中不可为了压低某个模型成绩减少其预算。

## 关于“全部 <80”

目前仅能说本 case 有较高难度潜力：堆叠、坐标变换、动态模式和删除后的状态一致性占据主要交互分。没有四模型实测证据前，不预测具体分数。

正式校准至少做 3 次独立有效运行/模型，报告每次分数与均值、标准差；把“本轮四模型均值 <80”和“全部 12 次运行 <80”分开。API 故障不计零分。若任何模型超过 80，保留结果；只能另起 v2，补充真实演示内容和公开要求，重新冻结四模型全部重测，不能修改 v1 评分器或挑最低 trial。

本版的确是公开 WebCompass 派生题，存在训练污染或记忆的可能。评估只能反映开发样本的表现；若作为论文正式测试集，应重新采集独立录屏和保留集。
