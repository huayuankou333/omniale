# DexJoCo bimanual assembly: develop a vision-based executable controller

Your goal is to make two Franka Panda arms with 16-DoF Allegro hands grasp a tray with the left hand, grasp a peg with the right hand, and insert the peg into the tray hole. Develop a reusable policy in `/workspace/policy.py` with `create_policy()` returning an object implementing `infer(obs)`. You have at most 7200 wall-clock seconds. Save a usable submission before the deadline. You may finish sooner if ready. No human-written solution will be added after you finish.

Observations have exactly these fields:

- `base`, `wrist_left`, `wrist_right`: uint8 RGB arrays (224,224,3).
- `state`: float array (46,), ordered right TCP xyz3 + wxyz quaternion4, left TCP xyz3 + wxyz quaternion4, right hand16, left hand16.
- `prompt`: the task instruction.

`infer(obs)` must return `{'actions': numpy_array}` with shape (30,44). Each row contains right TCP xyz3, right rotation vector3 (axis-angle radians), right hand joint targets16, left TCP xyz3, left rotation vector3, left hand joint targets16. These are absolute world-space targets, meters/radians, not deltas or normalized values. TCP targets refer to the attachment sites in the static robot model. Quaternion state uses wxyz, while SciPy defaults to xyzw; use `scalar_first=True` when appropriate. Right finger order: index4,middle4,ring4,thumb4; left finger order: ring4,middle4,index4,thumb4. XYZ and orientation commands are tracked by the original operational-space controller. Joint limits, mounting transforms, object geometry, nominal scene and camera calibration are available in `/public/assets/arena_arm_hand_bimanual_assembly.xml` and its includes. These files are static priors; actual object poses and table height vary per episode.

You have Python, NumPy, SciPy, Pillow, MuJoCo, and the shell and image-viewing tools of the coding agent. No additional Internet or external models are available. Your final policy must work with these installed packages and local static assets. It must not call the development simulator or any network service during inference. Use only `obs`, your submitted files, public static assets, and internal controller memory. Never attempt to read privileged environment state, hidden test files, demonstrations, or another model's submission.

Development simulator: import `/workspace/dev_client.py`. `SimClient().reset('rand_obj')` or `reset('rand_full')` returns `(obs,info)`. `step(actions)` accepts 1 to 30 rows of 44 absolute targets and returns `(obs,info)`. `observe()` returns the current observation without a physics step. `save_images(obs, directory)` writes three PNGs and a state JSON for inspection with the image tool. `rollout(policy, condition='rand_obj', output='dev_rollout', max_steps=1500)` executes and saves a full development trial. This synchronous development helper is intentionally separate from formal inference. Each physical step renders three cameras and is slow on CPU; a full failed episode takes around 25 minutes. Run long rollouts in the background and inspect saved images/logs while they run. There are at most 12 resets during the development budget. The service provides independent development seeds, never formal seeds.

There are two formal conditions: object position/yaw and table height randomization (`rand_obj`), and additionally camera, light, and table appearance randomization (`rand_full`). The same frozen controller is tested in both. The original success event is sustained peg-to-hole-bottom contact for 30 consecutive control steps; no partial credit. Each episode lasts at most 1500 control steps (physics_dt .002, control_dt .02).

Formal testing uses the unmodified upstream asynchronous evaluator. It replans when its buffered actions fall below 80% of a 30-step chunk, timestamps chunks, blends overlapping plans, discards stale actions, and continues holding/stepping the physics while waiting for inference. There is no reset flag or simulator step index in formal observations. Your controller should handle episode restarts using the available observations; avoid counting inference calls as if each call always executed exactly 30 control steps. The policy server persists across episodes. Final evaluation cannot use simulator client calls. Final interface errors will be recorded as invalid submissions rather than successful control.

Suggested workflow: inspect the static model and initial development images, implement a controller, test and revise with the available feedback, then leave `/workspace/policy.py` and any supporting local modules/parameters plus a short `SUBMISSION.md` explaining your method and observed development results. Do not edit `dev_client.py` to fabricate results or alter the task. Do not report imagined success rates.
