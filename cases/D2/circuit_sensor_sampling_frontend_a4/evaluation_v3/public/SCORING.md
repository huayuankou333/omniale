# 评分与失败处理（草案）

原题验收按复制的上游程序原样运行，包括原有 fail-fast 和 nominal gate。不能把 blocked 项补记为通过，也不能删除原题难点。

设 O 为原题通过检查数，N 为原题检查总数，A 为新增通过组数，M 为新增组数：

`score = round(100 * min(O/N, A/M), 2)`。

`task_success = 1` 仅当交付合法、原题全部通过、新增全部通过、全部要求的测量完整有效；否则为 0。分别输出 `original_passed/total`、`added_passed/total` 和原始数值，不把总分当成难度校准结论。此公式在模型试验前定义，不沿用 B1 的五组 20 分体系。

缺失/空提交、非法器件或接口、原始平台被改写、缺少必交 DESIGN.md：`invalid_submission`，0 分。平台或设备政策不能由模型自己声明通过。DESIGN.md 只检查存在及四个必需章节；不对文笔加分。

有效运行中的仿真不收敛、超时、NaN、缺少波形或测量：对应新增整组 0 分，`task_success=0`，其余已经完整证明的组仍可计分。原题自身失败处理保持原样。缺失值绝不补零当作零误差。

Docker 无法启动、PDK/镜像缺失、评测器异常等基础设施故障：`infra_error`、`score=null`，暂停该次结论；修复后对同一个冻结提交重跑，不能误报为模型能力失败。只有确认是电路本身数值失败后才按前段计分。

`tools/score.py` 是严格的聚合器，输入必须由可信验收端产生；它不运行仿真、不检验报告真实性，不能直接接收模型自报的通过项。正式 runner 尚未接入，当前没有正式成绩。未来 runner 必须逐组核对完整工况集合、测量有效性、提交哈希和原题输出，再产生聚合输入。
